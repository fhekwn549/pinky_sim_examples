벽·물체 만들기

지도를 만들려면 먼저 돌아다닐 공간이 있어야 합니다.
Gazebo world는 <model>의 모음이고, 벽 하나도 상자 모양 model 하나입니다.
상황에 맞는 방법을 고르세요.
MuJoCo에서 되는 것과 안 되는 것은 이 섹션 끝의 MuJoCo에서는 표에 있습니다.

SDF 직접 쓰기원리를 이해할 때. 물체 한두 개
레이아웃 YAML → world다시 쓸 맵. 이 패키지의 기본 방식
실행 중 추가·삭제장애물을 잠깐 놓아 볼 때. world 파일은 그대로
Gazebo 창에서 그리기모양을 눈으로 빠르게 잡을 때

SDF 한 덩어리 = 벽 하나

<model name="wall_back">
  <static>true</static>                        <!-- 안 움직이는 물체 -->
  <pose>0.2 1.385 0.125 0 0 0</pose>           <!-- x y z roll pitch yaw : 물체 "중심" -->
  <link name="link">
    <collision name="collision">               <!-- 부딪힘·라이다가 보는 모양 -->
      <geometry><box><size>2.04 0.02 0.25</size></box></geometry>
    </collision>
    <visual name="visual">                     <!-- 눈에 보이는 모양 -->
      <geometry><box><size>2.04 0.02 0.25</size></box></geometry>
    </visual>
  </link>
</model>
실수증상바로잡기
pose z를 0으로 둠벽이 바닥에 반쯤 묻힘z = 높이 ÷ 2 (높이 0.25 m면 0.125)
<collision> 없음로봇이 통과하고 라이다에도 안 보임visual과 같은 geometry로 collision 추가
world에 Sensors 플러그인 없음/scan이 아예 안 나옴gz-sim-sensors-system 포함. 공식 empty.world를 복사해 시작
벽 높이가 0.125 m 이하Gazebo엔 보이는데 지도·장애물 감지에 없음라이다 평면보다 높게(이 패키지는 0.25 m)

레이아웃 한 줄 → SDF 변환기

레이아웃 YAML에는 "바닥 중심 좌표 + 크기"만 적습니다.
make_world가 중심 높이, 벽 길이·각도를 계산해 SDF로 바꿉니다.

색·텍스처 입히기

      
모양은 <geometry>, 겉모습은 <visual> 안의 <material>이 정합니다.
색과 텍스처는 눈에만 보이고 라이다·충돌에는 영향이 없습니다(카메라에는 찍힘).


      
단색material

        
<material>
  <ambient>0.9 0.45 0.35 1</ambient>    <!-- 그늘에서 보이는 색 -->
  <diffuse>0.9 0.45 0.35 1</diffuse>    <!-- 빛 받는 면의 색. 보통 ambient 와 같게 -->
  <specular>0.2 0.2 0.2 1</specular>   <!-- 반짝임 (선택) -->
  <emissive>0 0 0 1</emissive>         <!-- 스스로 빛남. 램프·LED 표현 (선택) -->
</material>

        
값은 0~1 (r g b a).
레이아웃 YAML에서는 color: [0.9, 0.45, 0.35] 한 줄로 ambient·diffuse가 함께 들어갑니다.
실행 중 추가는 --color 0.9 0.45 0.35. 가상 장치 패널의 램프 색이 Gazebo에서 바뀌는 것도 이 ambient·diffuse·emissive를 실행 중에 바꾸는 방식입니다.


      
이미지pbr albedo_map

        
<material>
  <ambient>1 1 1 1</ambient><diffuse>1 1 1 1</diffuse>       <!-- 흰색 = 이미지 원래 색 -->
  <pbr><metal>
    <albedo_map>../textures/brick.png</albedo_map>           <!-- world 파일 기준 상대 경로 또는 절대 경로 -->
  </metal></pbr>
</material>

        
# 레이아웃 YAML: 경로는 YAML 파일 기준. make_world 가 world 파일 기준으로 바꿔 적는다
- {name: brick_wall, type: wall, from: [0, 1], to: [1, 1], texture: ../textures/brick.png}

# 실행 중 추가: 절대 경로로 바꿔 넘긴다 (-string 으로 넘긴 SDF 는 기준 위치가 없어서)
ros2 run pinky_sim_examples spawn_object box --at 0.45 0 --texture ~/textures/brick.png --name brick

메시 모델dae · obj · glb

        
실제 물건처럼 생긴 모델은 도형 대신 메시 파일을 씁니다.
메시 파일 안에 재질·텍스처가 들어 있어서 <material>을 따로 적지 않아도 됩니다.

        
my_cup/                         # 모델 폴더 (GZ_SIM_RESOURCE_PATH 경로 안에)
├── model.config
├── model.sdf
├── meshes/my_cup.dae           # 또는 .obj, .glb
└── materials/textures/*.png

<!-- model.sdf 의 visual -->
<geometry><mesh>
  <uri>model://my_cup/meshes/my_cup.dae</uri>
  <scale>1 1 1</scale>              <!-- mm 단위 모델이면 0.001 -->
</mesh></geometry>

<!-- world 에 놓기 -->
<include><uri>model://my_cup</uri><pose>0.5 0 0 0 0 0</pose></include>

        
공식 pinky_gz_sim의 shelf 모델이 이 구조입니다.
공식 launch는 GZ_SIM_RESOURCE_PATH에 pinky_gz_sim/models와 ~/.gazebo/models를 넣습니다.
직접 만든 모델 폴더는 다시 빌드해도 지워지지 않는 ~/.gazebo/models/에 두면 model://로 찾을 수 있습니다.
이 방식은 이번에 직접 실행해 보지 않았습니다.


    


    

      
MuJoCo에서는

      
같은 world 파일을 MuJoCo도 읽습니다(MuJoCo로 실습하기).
다만 MuJoCo는 시작할 때 world와 로봇을 모델 하나로 묶어 두고 그대로 돌리기 때문에, 물체는 실행 전에만 정할 수 있습니다.
아래 표는 시험용 world(빨간 상자, 텍스처 상자, 파란 기둥, 밀리는 캔, 대각선 벽)를 MuJoCo로 띄워 확인한 결과입니다.

      

        
Gazebo에서 한 것MuJoCo대신 이렇게

        
          
SDF 직접 쓰기됨상자·원기둥·구·메시, model:// 포함을 읽음

          
레이아웃 YAML → make_world됨같은 world 파일을 mujoco_sim.launch.py world_name:=…로 실행

          
실행 중 추가·삭제 (spawn_object)안 됨레이아웃을 고치고 make_world 후 다시 실행

          
Gazebo 창에서 그리기안 됨MuJoCo 창에는 도형을 추가하는 도구가 없음. 레이아웃으로 관리

          
단색 (color → <diffuse>)됨그대로 반영

          
이미지 텍스처 (texture)상자·원기둥은 무시흰 상자로 보임. 바닥 같은 평면에만 적용(공식 코드 기준)

          
밀리는 물체 (static: false)고정됨로봇만 움직일 수 있음. 캔을 밀면 로봇이 막힘

          
라이다보다 낮은 물체같음지도·코스트맵에 안 남음(Nav2 실습장의 턱이 그 예)

        
      

      

        
        
<!-- MuJoCo 가 만든 모델(~/.cache/pinky_mujoco/scene.xml) 일부 -->
<geom name="red_box/link/visual_3" rgba="0.9 0.1 0.1 1" type="box" … />
<geom name="tex_box/link/visual_5" rgba="1 1 1 1" type="box" … />
<geom name="can/link/visual_9" rgba="0.1 0.8 0.2 1" type="cylinder" … />
<freejoint name="floating_base" />   <!-- 움직이는 관절은 로봇 하나뿐 -->

      

      
밀리는 캔 확인: 로봇에 0.15 m/s 직진을 4초(0.6 m) 보냈는데, 정답 위치로 0.268 m에서 멈췄습니다.
캔 앞면(x 0.32 m)에 닿은 자리입니다.
MuJoCo 전용 YAML 상자 목록(pinky_mujoco/worlds/room.yaml)도 있지만 형식이 다르고(중심 높이·전체 크기, 색 지정 없음) Gazebo에서는 못 씁니다.
두 시뮬레이터에서 같은 맵을 쓰려면 레이아웃 YAML → make_world로 만든 SDF를 쓰는 편이 낫습니다.

    

  


  
  

    

      
SLAM · slam_toolbox

      
지도 만들기

레이아웃과 겹쳐 보면 무엇이 지도에 남고 무엇이 빠졌는지 보입니다.

    

    

      

        

          

            
            
            
          

        

        

          
          
        

        

          점유 172칸
          빈 공간 918칸
          모름 254칸
          레이아웃: 라이다에 보이는 높이
          레이아웃: 라이다보다 낮음

벽과 칸막이는 지도에 남았고 선반 3개(높이 0.11 m)는 라이다 평면(0.125 m)보다 낮아 비어 있습니다.

Nav2 · AMCL · nav2_simple_commander

      
Nav2 실습장

      
Nav2 연습용으로 따로 만든 3.0 × 2.4 m, 방 2개짜리 맵입니다.
공식 pinky_navigation 설정을 고치지 않고 그대로 돌려 목표 5개를 실제로 보내 본 결과를 함께 적었습니다.
실행은 튜토리얼 수준이고, 이 맵의 목적은 그 다음 단계인 파라미터를 바꿔 보고 코드로 목표를 보내는 연습입니다.

    

    

      

        

          
          
        

        

          목표 G1~G5
          낮은 턱 0.08 m (지도에 없음)
          문 0.8 m · 좁은 틈 0.2 m
        

        
레이아웃에서 계산한 지도(make_map, 0.05 m/칸, 69 × 57칸).
라이다(0.125 m)보다 높은 물체만 칠했습니다.
지도 좌표가 Gazebo 좌표와 같아서 공식 AMCL 초기 위치 (0, 0, 0)과 바로 맞습니다.

      

      
    
        
  1. 시뮬레이션
    
          
    ros2 launch pinky_sim_examples twin_arena.launch.py \
    world_name:=nav2_practice.world gz_world:=nav2_practice driver:=false
    
          
    driver:=false: 문장 명령 노드를 꺼서 Nav2와 /cmd_vel을 두고 다투지 않게 합니다.
    2. 
        
  2. Nav2 (공식 launch, 지도만 지정)
    
          
    ros2 launch pinky_navigation gz_bringup_launch.xml \
    map:=$(ros2 pkg prefix pinky_sim_examples)/share/pinky_sim_examples/maps/nav2_practice.yaml
ros2 launch pinky_navigation gz_nav2_view.launch.xml      # RViz: 2D Goal Pose 로 목표 찍기
    3. 
        
  3. 코드로 목표 보내기
    
          
    ros2 run pinky_sim_examples nav2_patrol          # G2 → G3 → G4 → G1
ros2 run pinky_sim_examples nav2_patrol G5       # 낮은 턱 위
    
          
    nav = BasicNavigator()
nav.waitUntilNav2Active(localizer='amcl')   # 응답이 한 번 사라지면 끝없이 기다릴 수 있음(아래 참고)
nav.goToPose(pose)                  # PoseStamped, frame_id='map'
while not nav.isTaskComplete():
    pass
print(nav.getResult())              # SUCCEEDED / FAILED / CANCELED
    
          
    미니 프로젝트의 "적재 A로 가서 대기 → B로 이동" 같은 미션 로직이 이 형태입니다(pinky_sim_examples/nav2_patrol.py).
    WSL에서 waitUntilNav2Active()가 AMCL 상태 응답을 못 받아 10분 넘게 멈춘 적이 있어서, nav2_patrol은 2초 제한으로 다시 묻는 wait_active()를 씁니다.
    이 방식으로 G2 → G3 → G4 → G1을 4/4 성공했습니다.
    4.

MuJoCo로 실습하기

      
공식 repo에는 시뮬레이터가 두 개 있습니다.
공식 README대로 ros2 launch pinky_bringup bringup_sim.launch.xml만 실행하면 기본값 때문에 Gazebo가 아니라 MuJoCo가 뜹니다(sim:=gz를 붙여야 Gazebo).
이 가이드의 앞부분은 Gazebo 기준이고 이 섹션은 같은 맵과 같은 Nav2를 MuJoCo로 돌리는 방법과 MuJoCo에서만 할 수 있는 실습을 다룹니다.

    


    
두 시뮬레이터의 차이

    

      
항목Gazebo (pinky_gz_sim)MuJoCo (pinky_mujoco)

      
        
시뮬레이션 속도 (이 PC, WSL)실제 시간의 약 0.67배약 1.0~1.08배

        
GPU센서 렌더링에 사용필요 없음(기본은 CPU로 그림)

        
정답 위치ROS로 나오지 않음/ground_truth 50 Hz

        
모터·속도최대 1.0 m/s, 단순 구동실물 XL330 가속 설정, 최대 0.25 m/s

        
라이다640점, 잡음 있음360점, 잡음 없음(광선 계산)

        
카메라1280 × 720640 × 360, CPU로 그리면 약 5 Hz

        
그 밖의 센서IMU, 초음파, D455 추가 가능없음

브리지가 하는 일이 다릅니다

      

        
Gazebogz sim별도 프로그램gz-transport →ros_gz_bridgeYAML에 적힌 토픽만 통역DDS →Nav2 · RViz

        
MuJoCobridge.py (ROS 노드)MuJoCo 라이브러리로 물리를 직접 돌리고 토픽을 만듦DDS →Nav2 · RViz

      

      
Gazebo는 자기 통신망이 있어서 그 토픽을 ROS로 통역하는 브리지가 따로 필요합니다.
MuJoCo는 통신망이 없는 물리 계산 라이브러리라서 공식 bridge.py가 시뮬레이션을 직접 돌리며 ROS 토픽을 만듭니다.
그래서 Gazebo는 브리지 설정이나 센서를, MuJoCo는 브리지 코드를 고쳐 토픽을 늘립니다.

실습: 정답 위치로 위치 추정 오차 재기

    
/ground_truth는 시뮬레이터가 아는 로봇의 실제 위치입니다.
실물에서는 알 수 없는 값이라 로봇이 스스로 추정한 위치(/odom, AMCL)가 얼마나 맞는지 시뮬레이션에서만 잴 수 있습니다.

    
# 터미널 1~2: MuJoCo + Nav2 (위 "SLAM · Nav2" 절)
# 터미널 3: 1초마다 오차 출력, Ctrl+C 로 요약
ros2 run pinky_sim_examples pose_error
# 터미널 4
ros2 run pinky_sim_examples nav2_patrol

    
주행  4.63 m | 정답 ( 1.09,  1.15) | odom   1.9 cm  0.8° | amcl   1.3 cm  0.3°
주행  8.36 m | 정답 ( 0.69, -0.24) | odom  91.7 cm 81.8° | amcl  18.0 cm  9.9°
--- 요약 (주행 8.62 m)
odom : 평균 67.5 cm / 최대 142.9 cm, 방향 평균 72.3° / 최대 172.0° (159회)
amcl : 평균 29.8 cm / 최대 73.5 cm, 방향 평균 25.4° / 최대 69.8° (159회)

    

      
잘 갈 때 (주행 8.2 m까지)
G2 13.2 s · G3 14.9 s · G4 22.0 s
odom 오차 0.1~2.7 cm, AMCL 오차 0.3~23 cm였습니다(2회 모두 비슷).
시뮬레이션은 바퀴가 미끄러지지 않아 odom이 오히려 AMCL보다 정확합니다.
실물에서는 반대가 되는 경우가 많습니다.

      
함정: 지도에 없는 턱
G4 → G1, 101.8 s, 2회 모두 재현
출발점으로 돌아오다 지도에 없는 낮은 턱(0.08 m) 모서리에 걸렸습니다.
바퀴가 헛돌아 odom 오차가 143 cm·172°까지 쌓였고, AMCL도 73 cm까지 어긋났습니다.
그런데 Nav2는 G1을 "성공"으로 보고했습니다.
정답 위치는 (0.73, −0.24)로, G1에서 약 77 cm 떨어져 있었습니다.
Nav2는 AMCL이 추정한 위치로 도착을 판단하기 때문입니다.

      
해 볼 것
턱(low_step)을 레이아웃에서 지우고 다시 돌려 오차를 비교합니다.
xy_goal_tolerance를 줄여도 "성공"이 나오는지 봅니다.
미션 코드에서 "도착 성공" 뒤에 실제 위치를 한 번 더 확인하는 방법을 생각해 봅니다.

    

    
Gazebo에서 같은 맵을 돌렸을 때는 경로가 턱을 피해 가서 이 현상이 나오지 않았습니다(G1 오차 0.05 m).
같은 맵이라도 시뮬레이터마다 경로와 결과가 달라질 수 있습니다.


    
실습: 물리 설정 바꾸기

    
MuJoCo 물리 값은 공식 pinky_mujoco/config/mujoco.yaml에 있습니다.
일부만 덮어쓰는 방식이 아니라 파일을 통째로 바꾸므로, 복사해서 고친 뒤 넘깁니다.

    
cp $(ros2 pkg prefix pinky_mujoco)/share/pinky_mujoco/config/mujoco.yaml ~/my_mujoco.yaml
# ~/my_mujoco.yaml 수정 후
ros2 launch pinky_sim_examples mujoco_sim.launch.py physics_config:=$HOME/my_mujoco.yaml

    

      
값공식 기본값뜻

      
        
control.max_linear0.25 m/s직진 속도 상한. 0.10으로 바꾸자 0.25 m/s 명령에도 실제 속도가 0.099 m/s(정답 위치 기준)였습니다. 기본값에서는 0.247 m/s

        
motors.wheel_accel74.9 rad/s²실물 XL330 가속 설정(Profile Acceleration 200)을 옮긴 값

        
control.command_timeout0.5 s명령이 끊기면 멈추는 시간

        
contact.wheel_friction1.2바퀴 마찰. 줄이면 미끄러짐과 odom 오차가 늘어남(확인 안 함)

        
lidar.samples360라이다 점 개수

        
camera.width · fps640 · 15CPU로 그리면 자동으로 낮아짐(측정 약 5 Hz)

      
    

    
physics.timestep과 rates는 서로 정수배여야 합니다.
맞지 않으면 브리지가 시작할 때 오류를 냅니다.

URDF · sensor · bridge

      
센서 붙이기

      
공식 URDF는 고치지 않고 urdf/pinky_sim.urdf.xacro에서 불러온 뒤 덧붙입니다.
센서마다 ①~④ 단계를 그대로 따라가면 됩니다.

    

    

      
      
      
      
    


    

      
공식 기본 탑재 이미 달려 있어서 켜기만 하면 됩니다.
새 카메라를 달 때 따라 할 본보기로 보세요.

      
① 장착link + joint

        
<!-- pinky_description/urdf/pinky.urdf.xacro -->
<joint name="front_camera_mount_fixed_joint" type="fixed">
  <parent link="base_link"/>
  <child link="front_camera_mount"/>
  <origin xyz="0.020 0 0.0495" rpy="0 ${cam_tilt_deg/180*pi} 0"/>   <!-- 앞 2 cm, 위 5 cm, 아래로 cam_tilt_deg -->
</joint>

        
기울기는 launch 인자 cam_tilt_deg(이 예제는 8°)로 바꿉니다.

      
② 센서type="camera"

        
<gazebo reference="front_camera_link">
  <sensor name="camera" type="camera">
    <camera>
      <horizontal_fov>1.1519</horizontal_fov>          <!-- 66° -->
      <image><width>1280</width><height>720</height></image>
      <clip><near>0.1</near><far>100</far></clip>
    </camera>
    <update_rate>30</update_rate>
    <gz_frame_id>front_camera_link</gz_frame_id>
  </sensor>
</gazebo>

      
③ 브리지영상은 전용

        
ros2 run ros_gz_image image_bridge /camera/image_raw     # 영상 (launch_sim에 이미 있음)
# camera_info 는 parameter_bridge YAML 에
- ros_topic_name: "camera/camera_info"
  gz_topic_name: "camera/camera_info"
  ros_type_name: "sensor_msgs/msg/CameraInfo"
  gz_type_name: "gz.msgs.CameraInfo"
  direction: GZ_TO_ROS

        
영상은 ros_gz_image로 넘기면 compressed 같은 image_transport 토픽도 함께 생깁니다.

      
④ 확인실행해서 본 값

        
ros2 topic echo --once /camera/image_raw --field encoding     # rgb8
ros2 topic echo --once /camera/image_raw --field header.frame_id   # front_camera_link
ros2 run rqt_image_view rqt_image_view /camera/image_raw

        
2026-11-18 확인: rgb8, 1280 × 720, 프레임 front_camera_link.

    


    

      
가정 센서 · 실물 Pinky에 없음 RealSense D455를 올렸다고 가정한 예제입니다.
d455:=true일 때만 붙습니다.

      
ros2 launch pinky_sim_examples twin_arena.launch.py \
    world_name:=scan_room.world gz_world:=scan_room d455:=true

      
① 장착기둥 + 몸체

        
<link name="d455_link">
  <visual><geometry><box size="0.026 0.124 0.029"/></geometry></visual>   <!-- 124 x 26 x 29 mm -->
  <collision><geometry><box size="0.026 0.124 0.029"/></geometry></collision>
  <inertial><mass value="0.39"/> ... </inertial>
</link>
<joint name="d455_joint" type="fixed">
  <parent link="d455_mast"/><child link="d455_link"/>
  <origin xyz="0 0 0.075" rpy="0 ${pitch} 0"/>      <!-- pitch + 면 아래를 봄 -->
</joint>
<gazebo reference="d455_joint"><disableFixedJointLumping>true</disableFixedJointLumping></gazebo>

        
disableFixedJointLumping이 없으면 Gazebo가 고정 링크를 부모에 합쳐 d455_link TF가 사라집니다.
위치·각도는 xacro 인자 d455_x, d455_z, d455_pitch_deg로 바꿉니다(위 측면도 슬라이더와 같은 값).

      
② 센서rgbd_camera

        
<gazebo reference="d455_link">
  <sensor name="d455" type="rgbd_camera">
    <topic>d455</topic>              <!-- d455/image, depth_image, points, camera_info -->
    <update_rate>15</update_rate>
    <gz_frame_id>d455_link</gz_frame_id>
    <camera>
      <horizontal_fov>1.5184</horizontal_fov>              <!-- 87° -->
      <image><width>640</width><height>360</height></image>
      <clip><near>0.6</near><far>6.0</far></clip>
      <noise><type>gaussian</type><mean>0</mean><stddev>0.005</stddev></noise>
    </camera>
  </sensor>
</gazebo>

좁은 라이다로 흉내 내고 실기와 같은 토픽으로 바꿔 냅니다.

      
① 장착이미 있음

        
공식 URDF의 ultrasonic_link(base_link 앞 2.7 cm, 위 0.9 cm)를 그대로 씁니다.

② 센서좁은 gpu_lidar

        
<gazebo reference="ultrasonic_link">
  <sensor name="ultrasonic" type="gpu_lidar">
    <topic>us_scan</topic>
    <update_rate>20</update_rate>
    <lidar>
      <scan>
        <horizontal><samples>9</samples><min_angle>-0.13</min_angle><max_angle>0.13</max_angle></horizontal>
        <vertical><samples>5</samples><min_angle>-0.13</min_angle><max_angle>0.13</max_angle></vertical>
      </scan>
      <range><min>0.02</min><max>3.0</max></range>   <!-- 실기 field_of_view 0.26 rad, 0.02~3.0 m -->
    </lidar>
  </sensor>
</gazebo>

      
③ 브리지+ 변환 노드

Gazebo에는 Range 센서 타입이 없어서 쓰는 방법입니다.

      
④ 확인

        
ros2 topic echo --once /us_sensor/range --field range

        
측정: 0.687 m (대상 앞면까지 계산값 0.673 m).

      아직 확인하지 못한 것
      
    
        
  • Nav2는 Nav2 실습장 맵에서만 실행해 봤습니다. 기본 경기장 지도로 Nav2를 돌려 보지는 않았습니다.
    • 
        
  • Nav2 시험 결과는 WSL에서 각 설정당 1~2회 돌린 값이라, 같은 목표도 실행마다 경로가 달라질 수 있습니다(좁은 틈이 그 예).
    • 
        
  • D455와 초음파 측정값은 같은 패키지의 센서 튜토리얼 작업에서 잰 값이고 이 페이지를 만들며 다시 재지 않았습니다.
    • 
        
  • D455 무게(0.39 kg)가 실물 Pinky 주행에 주는 영향은 시뮬레이션으로 알 수 없습니다.
    • 
        
  • 실물 Pinky와의 연결과 실물 센서 값은 시험하지 않았습니다. 자세한 목록은 패키지의 NOTES_미확인사항.md에 있습니다.
